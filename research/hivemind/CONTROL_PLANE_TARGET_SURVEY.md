# Control-plane security research targets

Checked **2026-10-06**. Scope: distributed AI training/inference and their scheduling, routing, and transfer infrastructure. DHT is no longer required. This is public documentation/source screening, **not vulnerability validation**; no deployments or public swarms were contacted.

**Recommendation:** add **KServe, Ray/KubeRay, vLLM, Kubeflow Trainer, and Kueue** to the existing shortlist. Trainer offers the most bounded first authorization experiment; **vLLM → Dynamo → NIXL** offers a broader inference study across component boundaries. Priorities reflect adoption evidence, a meaningful security boundary, and local audit feasibility—not estimated vulnerability counts.

Public swarm status updated **2026-10-07**: **Yes** means evidence of a current publicly joinable network was found; **No** means no current public swarm was found after searching (not proof that none exists); **Not verified** means not separately checked, or a published network exists but its current availability remains unclear. Public inference APIs alone do not count.

## Where to investigate

Local feasibility below is inferred from component interfaces, not demonstrated by running a harness. Pin a release/commit before auditing: main-branch designs and opt-in features may differ from the listed releases.

**KServe — production deployment and delegated credentials.** Its [adopter list](https://kserve.github.io/website/docs/0.19/community/adopters) names production users including Bloomberg, AWS, Red Hat, and Tesla. The [controller](https://kserve.github.io/website/docs/concepts/architecture/control-plane) resolves namespace-scoped versus deliberately shared cluster-scoped [runtimes](https://kserve.github.io/website/docs/concepts/resources/servingruntime), builds workloads, and supplies service-account [storage credentials](https://kserve.github.io/website/docs/model-serving/storage/providers/s3). **Question:** can a model developer restricted to namespace A induce access to B's credentials or violate configured artifact-destination restrictions? Establish permitted service accounts and destinations first; intentional credential delegation is not itself a bug. **Local:** Kubernetes plus mock storage/model endpoints, CPU. The [Knative identity-loss caveat](https://kserve.github.io/website/docs/admin-guide/serverless/servicemesh) is already documented.

**Ray/KubeRay — shared infrastructure across training and serving.** Ray has an [OSDI system paper](https://arxiv.org/abs/1712.05889); KubeRay documents [production use](https://docs.ray.io/en/master/kuberay/index.html). The newer opt-in [Kubernetes RBAC authentication](https://docs.ray.io/en/master/kuberay/user-guides/auth-rbac.html) delegates token and permission checks to Kubernetes. **Question:** do supported entry points consistently reject a namespace-scoped principal lacking access to the target RayCluster? Examine permission caching and deployment integration. The documented five-minute token cache is not an immediate-revocation promise; the [API reference](https://docs.ray.io/en/latest/cluster/kubernetes/references/api.html) excludes RayJob/RayService from this feature. **Local:** CPU Ray and Kubernetes. Ray explicitly [trusts all jobs/workers inside one cluster](https://docs.ray.io/en/master/ray-security/index.html); ordinary intra-cluster code execution and old exposed-dashboard findings are not new isolation failures. Check [existing advisories](https://github.com/ray-project/ray/security/advisories).

**vLLM — high reach and composable cache control.** Its [PagedAttention paper](https://arxiv.org/abs/2309.06180) anchors a major serving system. The [security guide](https://github.com/vllm-project/vllm/blob/main/docs/usage/security.md) documents secret per-tenant cache salts; [NIXL lease renewal](https://docs.vllm.ai/en/latest/design/nixl_kv_cache_lease/) adds request/engine metadata, heartbeats, and resource retention. **Question:** does an authenticating gateway preserve tenant/model/cache identity through routing and production KV connectors, preventing client input from substituting internal transfer metadata? Salt is caller input: the gateway must bind it to identity. **Local:** CPU metadata/connector tests first; real cache-transfer/output validation needs a model and suitable backend. Current [LMCacheMP code](https://github.com/vllm-project/vllm/blob/main/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py) carries cache salt. [ExampleConnector isolation](https://github.com/vllm-project/vllm/issues/53495), [lookup locks](https://github.com/vllm-project/vllm/issues/44096), [lease reaping](https://github.com/vllm-project/vllm/issues/58222), and [oversized-salt DoS](https://github.com/vllm-project/vllm/security/advisories/GHSA-wpww-v874-ph2p) are public already. Trusted-worker sockets are a documented assumption.

**Kubeflow Trainer — sharply defined cross-job authorization.** The [progress feature](https://github.com/kubeflow/trainer/blob/master/docs/user-guides/trainjob-progress.md) uses HTTPS and projected ServiceAccount JWTs with a namespace/job-specific audience; the [server](https://github.com/kubeflow/trainer/blob/master/pkg/statusserver/server.go) authorizes the URL target before writing status, using [audience construction](https://github.com/kubeflow/trainer/blob/master/pkg/statusserver/utils.go). **Question:** can A's valid worker token update B, including across namespaces? Separately characterize token validity after deletion/name reuse against the intended lifecycle policy. **Local:** two CPU TrainJobs in Kubernetes. **Qualification:** this feature is alpha, opt-in since v2.2 (`TrainJobStatus=true`); project popularity does not establish deployment of this particular feature.

**Kueue — tenant quotas and cross-cluster dispatch.** An [AI21-authored production account](https://cloud.google.com/blog/products/containers-kubernetes/ai21-trains-its-models-on-ai-hypercomputer) describes Kueue scheduling AI workloads. [Batch-user/admin RBAC](https://kueue.sigs.k8s.io/docs/tasks/manage/rbac/) separates job submission from queue administration; [MultiKueue](https://kueue.sigs.k8s.io/docs/concepts/multikueue/) copies jobs to worker clusters and synchronizes status. **Question:** can an ordinary batch user make the controller misassociate workload ownership, quota reservations, or remote job status after cancellation/recreation? Test configured namespace/queue policies with minimal user permissions. **Local:** one Kubernetes cluster initially, two for dispatch. Arbitrary kubeconfig-path reads were [fixed in v0.19](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.19.0); that known issue is not a fresh lead.

**TensorRT-LLM — coordinator and cache-transfer metadata.** [Disaggregated serving](https://nvidia.github.io/TensorRT-LLM/features/disagg-serving.html) has separate worker roles, coordinator routing/readiness, event ingestion, and returned `ctx_params`. **Question:** under a correctly configured trusted gateway, can an external caller's session/transfer metadata influence another authorized session or worker allocation? **Local:** coordinator/API stubs; full transfer requires suitable NVIDIA hardware/backend. [Subagent routing](https://nvidia.github.io/TensorRT-LLM/features/subagent-routing.html) explicitly says affinity headers are not authenticated relationships; simple header forgery without the required gateway is a known design limitation.

**SGLang — useful comparative target, with obvious leads already reported.** Its [paper](https://arxiv.org/abs/2312.07104) and [bootstrap registry](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/disaggregation/common/conn.py) expose a different PD worker/transfer design. **Question:** after establishing supported security controls, do registry/member lifecycle checks and routing implementations agree about eligible workers? **Local:** HTTP/FAKE-backend stubs; real KV validation needs a model. [Route poisoning](https://github.com/sgl-project/sglang/issues/39400) and [server-info exposure](https://github.com/sgl-project/sglang/issues/30166) are public reports, not findings verified here or novel leads.

**AIBrix — identity through an inference gateway.** The [paper](https://arxiv.org/abs/2504.03648) covers routing and orchestration; official [implementer guidance](https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/main/site-src/guides/implementers.md) attributes use to ByteDance's GenAI infrastructure, not a broad independent deployment census. [Gateway plugins](https://aibrix.readthedocs.io/latest/features/gateway-plugins.html) distinguish backend API-key validation from a caller-provided `user` quota header; no principal-to-header binding was established by this screen. **Question:** in deployments where a trusted auth layer derives/overwrites `user`, does identity remain bound to quotas, asynchronous jobs, and permitted model/profile choices? **Local:** gateway plus mock backend, CPU. [Shared ownership when rate limiting is disabled](https://github.com/vllm-project/aibrix/blob/main/docs/source/production/gateway.rst) is documented behavior.

**Xinference — supervisor/worker permission consistency.** [Internals](https://inference.readthedocs.io/en/stable/development/xinference_internals.html) describe distributed actors; the [auth system](https://inference.readthedocs.io/en/stable/user_guide/auth_system.html) adds model permissions and default authentication for fresh v3 installations. **Question:** are model-read/write/register permissions consistently enforced across supervisor REST, worker endpoints, and actor RPC under the documented deployment boundary? **Local:** CPU/mock model. Exact worker-subgroup formation needs confirmation; check [security advisories](https://github.com/xorbitsai/inference/security/advisories) before selecting a lead.

**NIXL — audit a shared component through its callers.** [Metadata exchange](https://docs.nvidia.com/nixl/getting-started/quick-start/) advertises registered memory and peer endpoints via direct TCP, etcd, or application channels. Its [trust guidance](https://github.com/ai-dynamo/nixl/blob/main/.agents/skills/nixl-python-api/references/security-trust-boundaries.md) assumes trusted metadata; notifications are not authentication. **Question:** do serving callers bind authenticated peer/request context to descriptors and reject stale/reused registrations before initiating transfers? **Local:** CPU/DRAM metadata lifecycle first; RDMA/GPU access requires separate validation. This is a component/integration audit, not a standalone inference platform or a promise to tolerate arbitrary untrusted peers.

**Volcano — established AI scheduling with an existing security baseline.** [Named production adopters](https://github.com/volcano-sh/community/blob/master/adopters.md) include Huawei Cloud and Baidu. **Question:** can restricted job input or permitted plugin responses violate gang/queue ownership or availability guarantees? **Local:** Kubernetes with CPU jobs/mock extender. Read its [2025 security audit](https://volcano.sh/blog/volcano-2025-security-audit/) first: scheduler DoS from a compromised elastic service/extender was already fixed as CVE-2025-32777. New scheduling features are more useful than repeating audited issues.

## Ecosystem follow-ups and lower priorities

- **[Gateway API Inference Extension](https://gateway-api-inference-extension.sigs.k8s.io/reference/spec/):** strong cross-implementation study of namespace-local InferencePools and [ReferenceGrant/route authorization](https://gateway-api.sigs.k8s.io/docs/concepts/security/). Compare llm-d against the specification; inspect AIBrix's neighboring ext_proc integration separately, as its InferencePool/EPP implementation status was not established. The reference EPP is for conformance, not production. CPU Kubernetes harness.
- **[Grove](https://github.com/ai-dynamo/grove), [LeaderWorkerSet](https://github.com/kubernetes-sigs/lws), [KAI Scheduler](https://github.com/kai-scheduler/KAI-Scheduler):** real subgroup/gang formation and integration opportunities around ownership, namespace references, and topology policies. Observed stars ≈273/848/1.6k; recent releases in September/October. Prefer investigating them inside a Dynamo/KubeRay deployment. Grove remains alpha; these received a lighter screen than the shortlist.
- **[PyTorch/TorchElastic](https://docs.pytorch.org/docs/stable/elastic/rendezvous.html):** enormous potential reach, but its [security policy](https://github.com/pytorch/pytorch/blob/main/SECURITY.md) explicitly assumes trusted distributed peers. Audit platform isolation around rendezvous, rather than treating missing primitive authentication as new. **[DeepSpeed](https://github.com/deepspeedai/DeepSpeed/blob/master/docs/_tutorials/getting-started.md), [Megatron-LM](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/user-guide/training-examples.md), [MPI Operator](https://github.com/kubeflow/mpi-operator):** weaker independent targets; coordination largely inherits PyTorch/launcher/Kubernetes assumptions.
- **[verl/HybridFlow](https://seed.bytedance.com/en/public_papers/hybridflow-a-flexible-and-efficient-rlhf-framework), [OpenRLHF](https://github.com/OpenRLHF/OpenRLHF):** valuable representative RL workloads for Ray integration. OpenRLHF's [remote-reward authentication report](https://github.com/OpenRLHF/OpenRLHF/issues/1317) is already public; regression/response-binding work can follow its fix. Neither screen demonstrated a training attack.
- **[DistServe](https://github.com/LLMServe/DistServe):** important [disaggregation paper](https://arxiv.org/abs/2401.09670), but the artifact inherits Ray and its example needs multiple GPUs; use as a design reference before prioritizing a separate audit. **[TGI](https://github.com/huggingface/text-generation-inference):** archived March 21, 2026. PANDA still lacks a verified public implementation. Petals is excluded per the research preference.

Retain **Dynamo, Mooncake, llm-d, and LMCache** from the [initial survey](DHT_PROJECT_SURVEY.md). For impact evidence, Mooncake has a [FAST 2025 system paper/deployment account](https://www.usenix.org/conference/fast25/presentation/qin). In a combined serving audit, check the documented [Dynamo trust boundaries](https://docs.nvidia.com/dynamo/dev/security/secure-deployment-guidelines), pool authorization, cache identity, and registration lifetime across these integrations.

## Research decision

Start with **Trainer's cross-job status authorization** for a small, falsifiable local experiment. For a larger paper, compare **identity and control-state preservation across vLLM/Dynamo/NIXL and another serving stack**, or **cross-namespace/job ownership across KServe/Trainer/Kueue**. Record the promised boundary, attacker permissions, version, control case, and raw traces before claiming an attack. A finding spanning integrations could have broader impact, but no such finding is established here.

Read [Breaking the Bulkhead](https://arxiv.org/abs/2507.03387) before designing the Kubernetes track: cross-namespace operator references are an existing research area. Public issue/advisory screening here is not an exhaustive novelty search. For any confirmed result, use the project's private security process—e.g. [KServe](https://github.com/kserve/kserve/blob/master/SECURITY.md), [Trainer](https://github.com/kubeflow/trainer/blob/master/SECURITY.md), [Kubernetes/Kueue](https://github.com/kubernetes-sigs/kueue/security), or [NVIDIA PSIRT/NIXL](https://github.com/ai-dynamo/nixl/security).
